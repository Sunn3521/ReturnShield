# ReturnShield AI — 3-minute hackathon demo

## 0:00–0:25 — Problem

“ReturnShield predicts return-abuse risk at the moment a merchant receives a return request. Instead of using a simple fraud yes/no rule, it converts calibrated risk into a cost-sensitive operational action: approve, verify, or manual review.”

## 0:25–1:00 — Operations Overview

1. Open **Operations Overview**.
2. Start the live server.
3. Leave the page open and show the live KPIs and charts changing without switching tabs.
4. Point out that the live stream uses synthetic transactions with changing risk regimes.
5. Hover over a graph bar or pie slice to show the contextual data tooltip.

Key point:

> The live dashboard updates operational data continuously while the static page shell remains stable.

## 1:00–1:35 — Return Investigator

1. Open **Return Investigator**.
2. Open the **Return Request to Inspect** selector.
3. Choose a high-risk return.
4. Show:
   - risk probability
   - decision
   - expected merchant loss
   - return history
   - refund history
   - return velocity
   - linked-account signals
   - key risk signals
   - operational summary
   - merchant protocol
   - customer communication

When live mode is active, reopen the selector later to show that the available return list has been refreshed without changing the investigation workflow.

## 1:35–2:00 — Coordinated-account detection

Open **Cluster Explorer**.

Show the relationship graph between:

```text
High-risk customer
       |
       +---- shared device
       |
       +---- shared address
       |
       +---- shared payment fingerprint
```

Explain that shared infrastructure is treated as a risk signal, not proof of fraud.

## Important presentation rules

Do not claim:

- real-world fraud prevalence from the synthetic generator
- production-grade accuracy from synthetic evaluation
- that shared device/address/payment data proves fraud
- that the LLM itself determines fraud risk
- guaranteed merchant savings outside the stated synthetic benchmark

## Technical strengths to mention

### 1. Point-in-time correctness

Historical features are computed only from events that occurred before the return request timestamp, preventing future-information leakage.

### 2. Cost-sensitive policy

Decision thresholds are selected on validation data using explicit false-positive, false-negative, verification, and manual-review costs.

### 3. Rare-event evaluation

PR-AUC and business cost are emphasized over naive accuracy because abusive returns are a minority class.

### 4. Coordinated-account signals

The network layer finds suspicious relationships that may be invisible when each customer is evaluated independently.

### 5. General-purpose AI chat

The chatbot can answer ordinary questions as well as use ReturnShield tools for current operational data and allow-listed actions.

## Final one-line pitch

> **ReturnShield predicts return-abuse risk at request time, turns that risk into a cost-optimized merchant action, and gives operators an explainable live system and AI assistant to investigate and act.**
